# 2. PROJECT IDENTITY

**Name:** OQVIAN PERIVANT

**Category:** External Attack Surface Management, Exposure Intelligence, Asset Monitoring and Security Configuration Review.

**Tagline:** See what changed. Find what's exposed. Secure what matters.

## Product purpose

OQVIAN PERIVANT demonstrates how an organization could identify unexpected changes in its approved external-facing infrastructure.

The product's fundamental questions are:

- Which infrastructure assets are approved?
- Which network services are expected?
- What was observable during the previous assessment?
- What is observable now?
- What has changed?
- Is the change approved?
- Which changes could introduce security concerns?
- Who is responsible for investigating the change?
- Was the issue resolved?

The product transforms infrastructure observations into actionable security investigations.

## Main product differentiator

**Change-focused security intelligence instead of another isolated scan report.**

The system must demonstrate not only that a service exists, but whether it is new, expected, approved, changed or requires investigation.

# 3. THE REAL-WORLD BUSINESS PROBLEM

Organizations manage servers, applications, cloud environments, domains and network services.

Over time, their external attack surface changes.

Examples include:

- A new administration port becomes reachable.
- An internal management interface is unintentionally published.
- A forgotten application remains available.
- An approved service is removed unexpectedly.
- DNS records change outside an approved maintenance window.
- A certificate changes unexpectedly.
- A service is deployed without an associated change request.

These changes are not automatically malicious.

However, a security team needs to understand them.

A conventional one-time inventory may not identify when a change occurred or whether it was authorized.

PERIVANT demonstrates ongoing comparison between an approved infrastructure baseline and newly observed conditions.

## Business value

The system could help organizations:

- Recognize unexpected services.
- Track changes to internet-facing infrastructure.
- Reduce unmanaged exposure.
- Identify responsible asset owners.
- Investigate unauthorized changes.
- Verify remediation.
- Maintain evidence-backed security records.
- Explain infrastructure risk to management.

The current build demonstrates these workflows without scanning real customer networks.

# 6. IMPORTANT SAFETY AND ACCURACY REQUIREMENT

External Attack Surface Management normally involves observing assets reachable from external networks.

**Our demonstration will not establish actual public internet exposure.**

Instead, it will combine:

1. Real, authorized localhost network-service observations.
2. Fictional infrastructure inventories.
3. Synthetic external-exposure snapshots.
4. Actual change-detection and incident-management logic.

The UI must clearly distinguish these categories.

## Required source labels

**LOCAL LAB OBSERVATION**
A service observed by connecting to an application-owned service bound to localhost.

**SYNTHETIC EXTERNAL SNAPSHOT**
A fictional observation representing how an external-facing environment might appear.

**APPROVED CONFIGURATION**
A predefined service or infrastructure policy.

**DETECTED CONFIGURATION CHANGE**
A real computed difference between two stored states.

**SIMULATED REMEDIATION**
A demonstration-only corrective action.

Do not describe a localhost service as publicly exposed.

A newly reachable local test port demonstrates the detection mechanism, not internet accessibility.

Never claim that a target is vulnerable merely because a TCP port is reachable.

# 9. SAFE LOCAL NETWORK LAB

This is the most important functional component.

Build a small controlled environment containing application-owned local services.

Use Python's asyncio networking APIs.

Documentation:

https://docs.python.org/3/library/asyncio-stream.html

## Local lab rules

- Bind all demo listeners to 127.0.0.1.
- Never bind to 0.0.0.0.
- Do not scan arbitrary hosts.
- Do not scan public IP addresses.
- Do not accept unrestricted network targets.
- Allow only explicitly registered demo service ports.
- Use short connection timeouts.
- Limit concurrent connection attempts.
- Close connections after observation.
- Cleanly stop all listeners.
- Do not require root privileges.
- Do not start external daemons.

## Lab service configuration

Create three service roles:

**Web Application**
- Approved.
- Normally reachable.
- Harmless local HTTP response.

**Application API**
- Approved.
- Normally reachable.
- Harmless local HTTP response.

**Management Interface**
- Not part of the initial approved baseline.
- Initially stopped.
- Started during the primary scenario.
- Returns a harmless static administration-page indicator.

Use ports such as 18080, 18081 and 19090 if available.

Handle port conflicts gracefully.

If a fixed port is occupied, choose a free permitted local port and record the chosen value.

Do not assume any fixed port will always be available.

## Important verification distinction

Opening the management listener demonstrates a newly reachable local service.

The corresponding fictional internet exposure scenario may illustrate how this would matter on a real public system, but it must remain labeled synthetic.

# 10. SERVICE OBSERVATION ENGINE

Implement a lightweight service-observation engine.

Use asynchronous TCP connection attempts only against the registered localhost test services.

Recommended function:

`asyncio.open_connection`

## Observation process

1. Read registered lab targets.
2. Validate that the target host is localhost.
3. Validate the target port is in the application's authorized registry.
4. Attempt a TCP connection with a timeout.
5. Record whether the connection succeeded.
6. Record the observed time.
7. Record error or timeout conditions.
8. Close the connection.
9. Store the observation.

## Observation statuses

- Reachable.
- Connection refused.
- Timed out.
- Observation failed.
- Not assessed.

Do not collapse all unsuccessful states into "closed."

A timeout does not prove that a port is closed.

## Evidence record

For every observation, preserve:

- Observation ID.
- Asset ID.
- Target address.
- Port.
- Transport.
- Result.
- Timestamp.
- Source mode.
- Scenario run ID.
- Error details, if any.

Do not send exploitation payloads or perform aggressive fingerprinting.

The initial implementation only needs service reachability.

# 12. DETECTION RULES

Implement deterministic detection rules.

The following thresholds and priorities are demonstration policies.

## R001 — Unexpected Newly Reachable Service

Trigger when:

- A registered service was not reachable in the previous successful observation.
- The service is reachable in the current successful observation.
- The change was not covered by an approved policy update.

Result:

**Newly Reachable Service**

Preserve previous and current evidence.

This does not prove public internet exposure.

## R002 — Unapproved Service

Trigger when:

- A service is observed as reachable.
- Its asset/port/protocol combination is not present in the approved service policy.

Result:

**Unapproved Network Service**

This rule is independent from R001.

A service can trigger both conditions.

## R003 — Unexpected Service Disappearance

Trigger when:

- A previously reachable approved service is no longer reachable.
- The observation is sufficiently reliable to classify the difference.

Result:

**Approved Service Unavailable**

Do not automatically claim a security incident or network attack.

Treat failed observations conservatively.

## R004 — DNS Configuration Change

Compare two synthetic DNS snapshots.

Supported records:

- A.
- AAAA.
- CNAME.
- MX.
- NS.
- TXT, when needed.

Trigger when a monitored record set changes outside an approved fictional change window.

Result:

**DNS Configuration Change**

Preserve exact before/after record sets.

Do not claim DNS compromise.

## R005 — TLS Certificate Metadata Change

Compare synthetic TLS certificate metadata snapshots.

Supported fields:

- Certificate fingerprint.
- Subject.
- Issuer.
- Validity start.
- Validity end.
- Subject alternative names.

Trigger when a relevant certificate value changes unexpectedly.

Result:

**TLS Certificate Metadata Change**

A legitimate certificate renewal should not automatically be classified as malicious.

## R006 — Missing Change Approval

Trigger when:

- A relevant configuration difference exists.
- The fictional change register has no matching approved change request.

Result:

**Unapproved Infrastructure Change**

Link the original configuration change and the approval-evaluation evidence.

## R007 — High-Concern Management Service

Trigger when:

- An unapproved service is classified in the fictional asset inventory as a management interface.
- The service is newly reachable or remains reachable contrary to its approved policy.

Result:

**Unexpected Management Service Exposure Concern**

The name of this finding describes a policy concern, not proven public exposure.

The priority should be higher when the fictional asset is marked business-critical or internet-facing in the scenario model.

# 14. DNS SNAPSHOT ENGINE

The demo needs DNS change detection but does not need live DNS provider integrations.

Build a deterministic snapshot-comparison module.

## Dataset

Use fictional names under the `.example` domain.

Example:

`portal.astergate.example`

Initial synthetic snapshot:

- A: 192.0.2.10
- MX: mail.astergate.example

Changed synthetic snapshot:

- A: 198.51.100.20
- MX: mail.astergate.example

The comparison should identify that the A record changed.

Store:

- Snapshot ID.
- Domain.
- Record type.
- Values.
- Observation time.
- Source mode.
- Scenario ID.

## Normalization

Normalize equivalent DNS answers correctly.

Record-set ordering must not produce false differences.

Preserve TTL information as metadata if included, but do not confuse a TTL-only change with an address change unless the rule explicitly covers TTL changes.

## Optional future feature

Read-only DNS queries for verified, user-controlled domains may be added in a later version.

Do not build unrestricted public-domain lookup or discovery into the first demo.

Documentation reference:

https://dnspython.readthedocs.io/en/latest/async-resolver-class.html

# 17. REMEDIATION VERIFICATION

2. Open the generated incident.
